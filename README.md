## 免登录（2026-08-06 实测确定的路线；浏览器部分 08-19 起停用）

X 未登录时 profile 页是降级渲染，但它带 **schema.org 微数据**
（`itemprop=identifier / datePublished / articleBody / author / ImageObject`）——
比登录后的 React DOM（`data-testid`）**更干净也更稳定**，因为那是给搜索引擎看的
结构化数据，正文完整、时间戳精确到秒、无 UI 噪声。

> 起初走的是「人工登录一次 + 持久化 profile」，但 Playwright 的 Chromium 会被
> Google/X 的反自动化拦住（用户实测连 Gmail 都登不了）。改走免登录后，
> **凭据、账号封禁、session 过期、登录反爬这四个问题一起消失。**

**代价（唯一的，至今仍在）**：每账号每轮只能看到约 5 条最新帖，且下滑不加载更多。
靠按账号发帖率自适应的轮询覆盖（2026-10-08 前一律 15 分钟，见文末）；
`saturation`（gap）检测负责在可能漏帖时显式告警。

三个实现细节（**浏览器路线，08-19 起已不走**；若哪天回到浏览器路线仍适用）：
- `wait_for_selector` **必须 `state="attached"`**——微数据是隐藏 `<meta>`，
  默认的 `"visible"` 永远等不到（实测把整轮抓取误判成结构失效）。
- 微数据解析**必须排除 `[itemprop="author"]` 子树**——作者块里也有
  `identifier`/`url`/`image` 同名字段，不排除会把作者 id 当帖子 id。
- **正文字段两个都要读：`articleBody` 与 `text`**。2026-08-14 X 把正文的
  itemprop 从前者改名成了后者（见下）。旧名留着：改名当天两种形态并存，
  且哪天改回去不该再瞎一次。

### ⚠️ 2026-08-14：正文 itemprop 改名，静默丢了三天内容

X 把 `articleBody` 改名为 `text`。`identifier` 与 `datePublished` **都还在**，
所以 post_id、时间、去重、翻页全部正常——**只有正文没了**。

**为什么三天没发现**：日志每轮打印 `看到 5 条`、`已证明无遗漏`，8 个账号全 ok，
结构失效清单为空。**现有检查只问"有没有 article"，从不问"有没有内容"。**
后果是链式且静默的：

```
空正文 → 分类器判成噪音 → 被 PUSH_BLOCKED 拦掉 → 用户什么都收不到
```

断点精确到日：08-13 空正文 0% → 08-14 跳到 52%（两种形态并存）→ 08-15 起 100%。

**现已加的守卫**：拿到 **≥3 条非置顶帖却全都没有正文** → `StructureError`，
**拒绝入库**。阈值 3 是因为单条纯图帖是正常形态，一整页全空不可能是巧合。

这条**必须 fail closed，不能只告警**——因为**入库即不可逆**：post_id 一落库
就永久标记"已见过"，之后再也不会重抓。等发现时 196 条的内容已随页面滚走、
永久丢失，只补回了页面上还看得见的 26 条。修复历史空行用 **UPDATE 不用
DELETE**（那些空行是事故证据，补字段不销毁事实）。

> **这类失败的通用形态**：管道"成功"但内容是空的。判据写在"有没有记录"上，
> 就永远看不见"记录是空壳"。任何抓取类检查都该同时校验**内容非空**。

### 2026-08-19：浏览器指纹被拦，改走 RSC（普通 HTTP GET）

X 开始拦 Playwright/headless Chromium 的浏览器指纹：**全新 profile 也一律
HTTP 403、正文全空**——不是 IP 被封、也不是 profile 被标记，是浏览器这条路
整条不通了。同一台机器上普通 HTTP GET 仍然 200（Python 默认 UA 就够）。

curl/urllib 拿到的 HTML **没有微数据**（那是浏览器执行 JS 后才有的），但服务端
把一份 React-Server-Components 的扁平化缓存直接渲染进了 HTML：
`client:VHdlZXQ6<b64>:details` 里有 `created_at_ms`/`full_text`，`:core` 指向作者，
`VHdlZXQ6…` 解码即 `Tweet:<post_id>`。这条路**比微数据更稳**——它是 X 自己
前端要用的数据，不是给爬虫看的附属品。顺带消掉一整类问题：不再需要
persistent profile、不会有 Chromium 进程残留。代码见 `parse_rsc_posts` 上方注释。

### 2026-08-27：解析块截到一半 —— 抓取全好，只是字段换了顺序

12:05 ET 八个账号同时"拿不到帖子"，15 分钟后告警。抓取这一层**完全正常**：
HTTP 200、226-270 KB、`:details` 键 18 个一个不少。坏的是**取块的边界**。

原来三处解析都用 `\{(.{0,N}?)\}` 拿块正文——非贪婪 `?` 停在**第一个** `}`，
等于默许了一个从没写下来的假设：*"我要的字段之前不会出现嵌套花括号"*。
当天 X 把三个 `={...}` 插进了 `full_text` 和 `created_at_ms` 中间：

```
full_text:"...", hashtag_entities:$R[]={__refs:$R[]=[]},
                 cashtag_entities:$R[]={__refs:$R[]=[]},
                 smarttags:$R[]={__refs:$R[]=[]},        created_at_ms:1655068521000}
                                              ↑
                              第一个 } 落在这之前，created_at_ms 永远拿不到
```

`if not ts or not tx: continue` 于是把六个块全数跳过 ⇒ 0 帖 ⇒ 结构失效告警。
**字段值一个都没变，值也没改名，只是换了顺序。**

**修法**：配平花括号扫描（并跳过 JSON 字符串，正文里本来就可能有 `{` `}`）。
字段怎么重排、中间插多少层嵌套都无所谓——**这是"再改也不会重演"与"下次还得
再修一遍"的分界**。三处（`authors:core` / `tweet:core` / `details`）同改：另两处
当时只是**碰巧**字段排在第一个 `}` 之前才活着，留着就是下一次的同一个坑。

**试过但否决**：拿 `,"client:` 当缓存记录分隔符来切块。看着更干净，但非空
`__refs` 列表内部长得一模一样——`__refs:$R[76]=["client:...:0","client:...:1"]`
——带两个以上 hashtag 的帖子恰好命中，然后**静默丢帖**，比原 bug 更坏。
`tests/test_x_relay.py::RscBlockBoundaryTest` 把这条否决也一并锁住。

> **这类失败的通用形态**：解析器把**位置**当结构。"我要的东西在第一个分隔符
> 之前"是对布局的猜测，不是对语法的解析；上游一改布局就静默失效。三次抓取
> 事故（08-14 字段改名、08-19 指纹拦截、08-27 字段换序）里，只有这次是我们
> 自己的解析太脆，而不是 X 断了路。

## 定位与铁律

- **信息中继 + 决策支持，不是 alpha**。不做预测、不下单。
- X 内容是**不可信输入**：可推送、可入库打分，**绝不进入任何下单路径**。
  本仓库不 import `ib_insync`、不占 clientId（`tests/test_x_relay.py` AST 扫描强制）。
- **静默失败显性化**：拿不到帖子（X 改版/被拦）→ 每个账号都连续失败 2 次即
  带冷却 TG 告警，恢复时发一次恢复通知；**拿到帖子但正文全空**（字段改名）→
  同等对待，拒绝入库（见上）；其他原因全灭 → 连续 3 次告警；窗口打满可能漏帖
  （gap）→ 告警；推送重试 5 次仍失败 → 告警。
- 定位是 **4-8 周验证探针**（回答「这些博主准不准」，供后续打分系统 A.10），
  不是长期管道。选择器脆弱是已接受的成本。

### 常驻进程跑着的时候能不能跑 `--once`？

**能，不用先 `pm2 stop`。**（2026-08-19 起抓取不再开浏览器，下面 ① 的 profile
冲突问题已不存在；② 的心跳约束仍然有效。） 结构失效告警的文案就是让人跑 `--once --dry-run`
去诊断的——故障时人最需要它，而那恰恰是常驻进程还在跑的时候，所以这条
必须成立。2026-08-09 实测确认过两件事：

**① Chromium profile 不冲突。** `run_once` 和 `do_login` 都用同一个
`runtime/x_profile` 开 `launch_persistent_context`，直觉上会撞 Chromium 的
单例锁。实测不会：Playwright 的 Chromium **不创建 `SingletonLock`**，两个
上下文同时开在这个目录上都正常工作（无竞争基线 32s，故意占住锁的对照 39s，
均 4/4 账号成功、退出码 0）。而且锁本来也只在每轮那几十秒里才可能被持有——
`launch_persistent_context` 在 `run_once` 内部开、结束即 `ctx.close()`，
900 秒周期里占空比约 4%，两轮之间连浏览器进程都没有。

理论上两个 Chromium 共用一个 profile 仍不是好习惯（单例锁存在就是为了防这个），
但这里的爆炸半径是零：该 profile **只存 guest cookie、无任何凭据**，
中继本来就跑在未登录态（心跳里 `logged_in: false`），坏了删掉重建即可。

**② 但 `--once` 绝不能写心跳**（已修）。诊断跑一次会把主仓库的
`data/runtime/heartbeat/x-levels-relay.json` 刷成新鲜的 `connected=true`——
而 watchdog 对「pm2 显示 online、进程其实卡死」的唯一探测手段就是心跳新鲜度
（`health_watchdog.py::bot_health_failure`）。于是：进程卡死 → 心跳变旧 →
watchdog 正要告警 → 人按提示跑一次诊断 → 心跳被刷新 → 告警消失 → 人以为
「跑一下就好了」，卡死的进程继续没人管。现在 `--once` 传 `write_hb=False`，
只有 `--loop` 写心跳；心跳的语义是「**守护进程**还活着并在循环」，
一次性诊断不算。三条测试锁住这个约束（含反向的：`run_loop` 不许关心跳）。

> 注意 `--once`（不带 `--dry-run`）会**真的推送**并导出简报文件；
> `--dry-run` 则绝不写 posts 表——它若把帖子标成"已见过"，真正的循环之后
> 就再也不会推它们（2026-08-07 实测被一次 dry-run 吃掉过 10 条新帖）。

## 部署

```bash
# TG_TOKEN 从已有进程环境取，不落盘（同主仓库模式）。
# 可选 X_RELAY_TG_CHAT_ID 指定独立 chat，缺省回落 TG_CHAT_ID。
cd ~/Documents/trading_x_relay
TG_TOKEN=... TG_CHAT_ID=... PATH=/opt/homebrew/bin:$PATH \
  pm2 start venv/bin/python3.11 --name x-levels-relay -- x_relay.py --loop
pm2 save
```

改代码后上线：先跑全部单测，再 `pm2 restart x-levels-relay`（环境变量随进程
保留，不需要 `--update-env`）。重启时旧进程会在 error log 留一条
`KeyboardInterrupt`，回溯里的源码行对不上——那是 Python 按旧行号读了新文件，
无害。重启后立刻全账号抓一拍，看日志里"下次间隔"一行确认调度正常。
推送消息的发送者名显示为主仓库机器人的名字（共用 `TG_TOKEN`），这是预期的。

主仓库 CLAUDE.md「规则 2」同样适用：部署后须在
`quantrift_index_future/health_watchdog.py::BOTS` 登记，否则进程挂掉无人知道。

心跳写的是**主仓库**的 `data/runtime/heartbeat/x-levels-relay.json`
（纯 JSON 约定，双方不互相 import；路径可用 `QR_HEARTBEAT_DIR` 覆盖）。

## 2026-08-08：推送口径反转 + 修静默丢失

### 一、白名单 → 黑名单（用户决定）

原设计只推 `index_*`。实测 38 小时后代价显形：Dayu 14 条里 8 条是个股
（`$spcx` `$arqq` `$aaoi` `$gdx`）——**正是用户认为他准的那部分，全被丢弃**。

用户口径：「不论 stock / index 还是其他期货、黄金、白银、原油，包括对政策的
评论，只要和交易有关的都要」。BTC 行情观点要推，代币项目推广不要。

真实 54 条回放验证：**推 39 / 拦 15，拦下的全是噪音，零误杀**。

回放还救回一条会被漏掉的：novicetrader888 的「多头不用太紧张…连续短时间超买…
继续持多设好止损」是实打实持仓观点，但无标的、无数字，旧口径掉进 `other`。
已为 `assume_index` 账号加「有行情语义即算观点」的路径。

**加密必须分两类**（真实回放发现）：「Pact 现已支持 BTC、ETH 兑换」提到主流币
却没有 TGE/KYC 硬词，只靠 `_PROMO` 拦不住会被当行情推出去。现要求
主流币 **+ 行情语义**（支撑/目标/做多/浪…）才算观点，配 `_PRODUCT_NEWS` 兜底。

### 二、静默丢失（真 bug）

```python
if not store.insert_post(post):
    continue                  # 已见过 → 永不重试
if should_push(...):
    if tg_send(msg):          # 失败返回 False
        store.mark_pushed()   # 只有成功才标记
```

**帖子先入库、再发送；发送失败什么都不做。** 下一轮 `insert_post` 返回 False
直接跳过——那条帖永久丢失，**无重试、无告警**。实测吃掉 2 条 `index_levels`
（Mancini 08-06 15:55、Dayu 08-06 18:08），大概率是 bootstrap 突发推送撞上
Telegram 单 chat 限流（约 20 条/分钟）。

修法与主仓库 `alert_outbox` 同源：新增 `push_attempts` 列 + 轮末重试队列，
只有 2xx 才 `mark_pushed`，失败留队列；5 轮仍失败发告警（不再静默）；
补发放慢到 1 秒/条避开限流。

> 注意：先前排查中「漏推 8 条」里有 6 条其实是 `PUSH_MAX_AGE_HOURS=12`
> 时效门挡的（防首轮回填刷屏），属合理设计。真 bug 只有 2 条。

## 已知限制

1. **每轮 5 条上限**（有置顶的账号实为 4 个新帖位）：高频账号靠自适应轮询追，
   仍接不上时 gap 告警会点名（首轮 bootstrap 不算）。
2. **图片里的点位抓不到**（当前 24%）：推送标 🖼 提示，`--stats` 跟踪占比，
   据此再决定是否上 vision。
3. **标的换算未做**：SPX ≠ ES ≠ SPY×10（fair value basis 漂移）。
   推送的是博主原话数字，**不能直接当 MNQ/MES 挂单价用**。
4. 分类器 v1 是启发式；分错只影响推送不影响台账，历史行可用升级后的
   分类器重打标签回放验证。
5. **打分系统（A.10）尚未做**——这才是「能长期活下去的唯一理由」，
   本服务只是它的数据采集端。
6. **免登录 syndication 接口不可用**（2026-10-08 实测首个请求即 429），
   想一次多看帖子目前没有替代来源；可见窗口只能靠轮询频率补。
7. **台账里 175 条历史帖的 `levels` 含链接数字造成的假点位**（10-08 前入库），
   未回改；打分系统使用前应先用当前分类器重算。

## 2026-10-08：按账号自适应轮询（取代一律 15 分钟）

**起因**：gap 告警点名 mentoviax。它 08-11 加入时实测约 2.7 小时一帖，到 10 月
已是工作日 45-51 帖/天、盘中 3.4 帖/小时、10 分钟能连发 6 帖；而它有置顶，
免登录页 5 条里只有 **4 个新帖位**。15 分钟一轮接不上：累计 21 次 gap，
9 月下旬起几乎每个交易日一次。zerohedge 更甚（95 次）。与此同时另 5 个账号
发帖率 ≤0.7 帖/小时，15 分钟一抓几乎全是"新 0 条"。

**否决的方案**：
- 全局缩短到 5 分钟——请求量 ×3，低频账号白抓，一次限流 8 个账号一起断；
- 移出名单——丢数据源；
- syndication 嵌入时间线接口（一次约 20 条）——10-08 实测首个请求即 `429`，免登录不可用。

**做法**（`PollScheduler` / `poll_interval`）：每个账号抓完后按**预期发帖率**
定下次间隔 = `FILL_TARGET / rate`，夹在 **5-15 分钟**。预期发帖率取两者较大值：
近 2 小时实际速率、过去 14 天同类日子（工作日/周末分开）同一时刻往后 1 小时
的平均速率——后者让它在**开盘前**就缩短，而不是爆发一个多小时后才追上。
刚出现 gap 的账号下次直接按最短间隔。

**上限仍是 15 分钟，任何账号都不比改前慢**（用户决定）。最初版本把低频账号
放长到 45 分钟、用省下的请求补给高频账号，总量还能降到 24 次/小时；但被否：
低频的 Dayu、novicetrader888、willem、gexedge **恰恰是质量最高的**，
推送晚半小时不可接受。所以这是**给高频账号加抓**，代价是请求量 +7%。

**预算**：滚动 1 小时 ≤40 次。距上次抓取满 15 分钟的账号**必抓**、不受预算
限制（这条保证"不比改前慢"，也防止高频账号饿死低频账号）；预算只决定
高频账号在两次必抓之间能额外抓几次，间隔短的优先。

**参数怎么定的**：用库里 09-24..10-08 的真实发帖时间回放（带预算，驱动真实
调度器代码；有置顶账号窗口 4、zerohedge 窗口 5）：

| 方案 | gap | 估计漏帖 | 平均请求/小时 | 滚动 1h 峰值 | 最长间隔 |
|---|---|---|---|---|---|
| 固定 15 分钟（改前） | 29 | 18 | 32.0 | 40 | 17 min |
| 自适应、上限 45min、预算 32、FILL 0.4（否决） | 4 | 0 | 24.1 | 35 | 50 min |
| 自适应、上限 15min、预算 32、FILL 0.4 | 24 | 4 | 32.1 | 41 | 17 min |
| 自适应、上限 15min、预算 40、FILL 0.4 | 2 | 0 | 36.5 | 45 | 17 min |
| **自适应、上限 15min、预算 40、FILL 0.75（采用）** | **3** | **0** | **34.3** | **42** | **17 min** |

预算卡在 32 等于没修：低频账号的必抓已占满 32，高频账号没有加抓余地。
FILL 0.4 与 0.75 的差别在噪声内，取请求更少的 0.75。它看似保守（帖位共 4 个），原因是发帖成簇：mentoviax 均值
3.4 帖/小时，但 10 分钟能连发 6 帖，按均值填一半帖位照样撑爆。
回放会低估——库里本就缺那些已漏掉的帖。

**随之改动的语义**（都有测试锁住）：
- 没有"轮"了：停摆告警的去抖改为**每个账号**都连续失败 ≥N 次（结构失效 2、
  其他 3），与改前阈值相同；
- 推送重试队列按时间节流到每 15 分钟一次，否则一两分钟一拍会让
  `PUSH_RETRY_MAX=5` 在几分钟内耗尽；
- 整拍异常时这批账号照常排期（按失败处理），否则它们一直"到期"、每分钟重抓。


## 2026-10-08：推送排版（Telegram HTML）

`format_push` 改为 `parse_mode=HTML`：首行是加粗的账号（链到 X 主页——裸写
`@handle` 会被 Telegram 当成 **TG 用户名**自动加链接，点过去是不相干的人）+
`#分类` 话题标签（点一下可在群里筛同类）；第二行时间 + `原帖 ↗`；正文进引用块，
超过 300 字折叠；点位用等宽字体。

顺带修掉两个一直存在的显示问题：
- **`S&amp;P 500`**：X 存的 `&` 是编码过的，分类器读的时候会还原，推送从没还原过；
- **t.co 短链**：只是图片/外链的跳转地址，从正文里去掉（原帖链接另有一行）。

**兜底**：所有帖子文字一律 `html.escape`。用库里 8589 条历史帖校验：转义后
0 条不合法；去掉转义则 434 条会被 Telegram 拒收（一次性回放校验；
行为由 `PushFormatTest` / `TgSendFallbackTest` 锁住）。万一仍被拒收（HTTP 400），
`tg_send` 立刻改发旧的纯文本格式（`format_push_plain`），**不进重试队列**——
格式错误重试多少次都一样错。告警消息仍是纯文本，不受影响。
